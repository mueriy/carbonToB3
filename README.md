B3Carbon
===

B3Carbon is a symbolic-execution-based verifier for [the Viper intermediate verification language](https://github.com/viperproject/silver). 

[The Viper project](http://www.pm.inf.ethz.ch/research/viper.html) is developed by the [Programming Methodology](http://www.pm.inf.ethz.ch/) group at ETH Zurich.

Use the instructions below to install B3Carbon. See [the documentation wiki](https://github.com/viperproject/documentation/wiki) for instructions on how to try out or install the Viper tools.

B3Carbon has been adopted from an existing backend, Carbon, by making it use [B3](https://github.com/dafny-lang/b3) instead of [Boogie](https://github.com/boogie-org/boogie). It does not yet support all features, and parts of the code remain unchanged (but are e.g. commented away).

Installation Instructions:
---

B3Carbon needs to be compile from source with the following steps:
* Install Z3 (see wiki above) and add it to PATH\
  (B3 requires z3 to be in PATH; environment variable Z3_EXE is ignored, so it does not need to be set)
* Clone this repository *recursively* by running:  
`git clone --recursive https://github.com/mueriy/carbonToB3`

And then  
* Compile and run with:  
  `sbt "set Compile / run / fork := true" "run [options] <path to Viper file>"`
* Alternatively, for a faster startup without compilation each time, build a `.jar` file:  
  `sbt assembly`  
  And then run with:  
  `java -jar ./target/scala-*/carbon.jar [options] <path to Viper file>`

If an error message shows `... Error initializing '['z', '3']': Cannot run program "z3": ...`, then Z3 is not in PATH.

Options
---
When running B3Carbon, the following options can be used.
* `--printOut` outputs the generated B3 program to the terminal
* `--print <PATH>` prints the generated B3 code to the given location
* `--b3Jar <PATH>` Manually-specified full path to B3.jar (should not be necessairy)
* `--check <CATEGORIES>` Given a comma-separated list of integers (e.g. `1, 5, 6`), all assertion categories matching one of the given numbers will use check instead of assert.
* `--dev <n>` shows information for development. See the section for developers below for more info. (n = 0 to 4, default 0) [Verifying the *code printouts* (generated by using `--print <PATH>` or `--printOut`) with B3 is not supported when n >= 1. Only the internal use of B3 works as usual.]

For Users:
---
B3Carbon is not yet fully finished. However, it can already be used to verify Viper code if only a certain subset of Viper featuers are used. 

It supports most pure Viper features, non-parametric domains, and most basic permission/Heap interactions. Features it does not yet support are parametric domains, predicates, fractional permission (or using the `Perm` type as real), any of the special Viper types (Set/Seq/Map/...), unique functions, and other, more advanced features. 

In general, verifying correctly written Viper code does not cause any error to appear, even if the Viper code contains unsupported features. To get some idea whether a used feature is supported or not, the `--def` flag could be used with a value of >= 1. B3Carbon will then output a list of currently unsupported parts of the project that were attempted to be used, sorted by the Viper feature that these methods are for. This was not developed for users, so if some part is needed for multiple features, only one of them is shown (whichever one is first on the todo list for further development). There are some unsupported parts that always show up (even if the corresponding feature is not used), but they can usually be ignored. If any others unsupported parts are shown, then an unsupported feature was used.

The output still calls this project carbon, since there is no official name yet (B3Carbon is just the temporary name for now).



For Developers:
---
B3Carbon is based on Carbon; i.e., we took the Carbon project and modified it for our purposes. The reasons behind changes from Carbon and B3Carbon should either be obvious or explained with comments. We also recommend reading the thesis to this project, "Implementing a New Viper Back-End Targeting B3" (link TBD) for further information. The main changes are the new AST nodes (see object `B3Nodes` in `B3Adapter.scala`) and the split-Heap approach. `B3Adapter.scala` is the only file with interactions with B3 (i.e. `B3.jar`). 

This project uses [this B3 version](https://github.com/dafny-lang/b3/tree/ea6e8a18dfe9e317d313de769291f989957dc5f2). This version adds domains to B3, but they currently do not work well, which is why we do not actually use them. Instead, we implemented our own system to support multiple concrete variations of "parametric" entities, although parametric domains will need to be supported differently.

All places that currently still need work are marked with either `B3 TODO`, `B3 LATER`, or `B3 ADVANCED`, depending on how soon it should probably be implemented. These tags are also always followed by the least advanced feature that needs it, as best as we could sort them. The next features that should be supported are currently in the 'LATER' category (e.g. predicate). There is also `B3 QUEST`, which explains an idea that could maybe implemented at the end in some capacity, as well as `B3 REAL`, which marks positions that can be updated when B3 supports the real typ (although, this might also be the case for some places marked with one of the first three marker types). All parts that where commented out using /* and \*/ that are placed at the start of the line are from Carbon and have not been supported/replaced yet. The /* may be followed by a comment about the/one feature it is needed for.

By setting the `--def <n>` flag, B3Carbon will output additional information (unless n == 0). Setting n == 1 will show an overview of unsupported parts of the code (in the B3Carbon-project) that would theoretically be executed right now. This shows when the implementation is not finished yet for some feature used in the Viper code. Setting n == 2 or 3 will also add empty statements to the code that are tagged with a description of which part of B3Carbon might want/need to insert additional statements at that location of the B3 code. These two infos together can be very helpful when supporting a new feature to see if some part that is required for this feature got forgotten somewhere. (See object `B3Development` in `B3Adapter.scala` to see the methods used to show these informations.)
